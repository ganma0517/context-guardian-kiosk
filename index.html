Context Guardian 是一套給 Claude Code 用的被動式上下文管理規則。任務跑得長、工具一次回傳一大包內容時，讓 Agent 自己判斷該壓縮、卸載，還是拆給子代理處理，不需要使用者盯著用量、手動喊停。

SECTION ONE 01 / 06

工具回傳的內容，
比對話還快堆滿視窗。

常見觸發情境

五種，見下方卡片

Claude Code 在長時間的任務裡，會把工具回傳的原始內容直接放進對話紀錄：Zotero 全文檢索、Google Drive 文件、Stata 執行紀錄、逐字稿，一份一份疊上去。跑到第十輪、第二十輪，這些原始輸出占掉的空間，早就超過真正在推理判斷的部分。

預設的處理方式是被動反應：使用者先感覺到變慢或出錯，再手動喊 /compact 壓縮。等到那個時候，審稿人的原文用字、變數的操作型定義，可能已經被摘要摘掉了，因為摘要不會知道哪段話之後還要逐字對照。

Context Guardian 要處理的，是把這個判斷提前：在工具即將回傳大量內容、任務準備跨很多輪之前，先套用規則，不等使用者提到「太長了」才反應。

TYPE A
大型工具輸出

工具即將回傳大量內容：Zotero 全文檢索、Drive 文件下載、Stata log、逐字稿讀取，或多次疊加的搜尋結果。

TYPE B
跨多輪的任務

任務預期會跨多個工作輪次，例如多階段的分析流程，或跨論文的設定檔建置。

TYPE C
數量超過門檻

處理中的檔案或文獻超過三份，或單一工具一次回傳超過五百行。

TYPE D
準備派工或彙整

準備把任務分給子代理處理，或正在收攏多個子代理回傳的結果。

TYPE E
階段切換

一個邏輯階段已經跑完，準備進到下一個獨立階段，例如一篇論文的文獻分析結束。

決策邏輯：三個判斷點

SECTION TWO 02 / 06

規則本身不複雜，重點在把「要不要處理」拆成三個先後的判斷，每個判斷都有明確的是非分支，Agent 照著走就好，不用每次重新想一遍。

判斷一
要不要卸載

工具即將回傳大量內容嗎？如果是，再問：這段內容需不需要逐字保留（引註原文、審稿意見、變數操作型定義）？需要就寫進暫存檔，對話裡只留路徑加三到五行摘要；不需要就直接摘成重點，原始輸出不進對話紀錄。

判斷二
要不要拆給子代理

任務可以拆成獨立子單元嗎，例如每篇論文、每份逐字稿、每個模型？可以就逐一派子代理處理，要求回傳結構化格式而不是自由文字；不行就由主線直接處理，但仍然套用卸載規則。

判斷三
要不要換 session

一個階段做完了，下一階段還需要這階段的中間過程嗎？不需要的話，先把結論寫回設定檔，再提醒使用者可以開新對話，不要讓舊階段的探索過程留在上下文裡等自動壓縮。

規則一：什麼絕對不能被摘要掉

SECTION THREE 03 / 06

摘要是一種
有損轉換。

核心提醒

摘要傾向把模糊處
美化成確定結論

有四類內容一旦被自動摘要，後續的任務就會失真：審稿人的原始文字，因為回應意見要逐字對應；變數的操作型定義與資料集代碼；統計模型的確切設定，例如估計方法、群集選項、插補次數；還有會被引用查核機制檢查的內容。這四類遇到壓縮，一律先抽出寫進檔案，不進摘要流程。

除此之外，像是工具呼叫的中間過程、已經讀完並下了結論的長文件全文、探索性搜尋的原始清單，都可以摘要或直接捨棄，只留結論。摘要之後，遇到不確定的地方要標「待查證」，不能自己補完，這正是摘要容易把模糊處講成定論的地方。

卸載 · TYPE A
先寫檔案

大型工具輸出一律先寫進暫存資料夾，對話裡只留檔案路徑加三到五行摘要。

卸載 · TYPE B
精準查閱

需要回頭找內容時，用行號或關鍵字定位擷取，不整份重新讀進對話。

卸載 · TYPE C
分層儲存

跨工作階段的長期結論寫回設定檔；暫存資料夾只放這次工作階段用完就丟的內容。

規則二：子代理只回結論不夠

SECTION FOUR 04 / 06

沒有可追溯的引用鏈，
主線沒辦法驗證。

回報格式

結論・依據・待驗證
三段式，缺一不可

子代理如果只回傳一段自由敘述的結論，主線沒有辦法核實，彙整的時候也容易把子代理原本標記為不確定的地方，講成確定的結果。固定格式因此有三段：結論用一到兩句話講清楚，支持依據要寫來源檔案加行號或頁碼，不能是敘述性的說明，最後列出有沒有無法確認來源的待驗證項目。

主線收到回報後，只把結論摘要進主對話，支持依據留在檔案裡備查，需要的時候再回頭核對。同樣的邏輯也用在思考預算的分配上：例行、格式化、確定性高的步驟用低思考預算，理論架構比對、審稿意見的實質回應這類真正需要判斷的步驟，才用高思考預算。

範圍過濾 · A
排除大型二進位

原始 PDF 與大型檔案改用已抽取出來的純文字版本，不把整份二進位檔案放進索引範圍。

範圍過濾 · B
排除暫存與版控目錄

.git、node_modules、統計軟體產生的暫存檔，一律排除在索引範圍外。

範圍過濾 · C
排除已完成的舊全文

已經進知識庫的逐字稿全文改用結構化輸出查詢，不再保留原始全文。

設計關鍵：怎麼讓它真的被動

SECTION FIVE 05 / 06

Skill 本身是按需載入的機制：Claude 要先判斷眼前的任務符合 Skill 的描述，才會去讀規則本體。問題在於，單步驟、看起來簡單的操作，例如「讀這份逐字稿」，即使規則明明適用，也可能因為不覺得需要動用 Skill 而被跳過。

要讓它真正被動，得在專案根目錄的 CLAUDE.md 放一段提醒。這個檔案每次工作階段開頭都會強制載入，不像 Skill 要等觸發判斷。把判斷責任從「要不要觸發」改成「一律先檢查」，兩層設計缺一不可：SKILL.md 放完整規則，CLAUDE.md 放觸發保證。

只有 SKILL.md

觸發靠 Claude 自行判斷「這個任務符不符合描述」。單步驟、看似簡單的操作容易被判斷成不需要，規則就被跳過。

加上 CLAUDE.md 提醒

每個工作階段開頭強制載入，把判斷題換成一律檢查的直接指令，才接近真正的被動：不用使用者記得喊它，它自己在背景把關。

設計啟示：能搬到哪些場景

SECTION SIX 06 / 06

這套規則處理的問題，不是 Claude Code 獨有：任何長時間執行的 Agent 系統，只要有工具輸出、多輪任務、多子系統協作，都會不斷把原始內容塞進工作記憶裡。三個設計原則抽出來，換到別的框架上邏輯一樣通。

原則一
分層保留

先分辨哪些內容必須逐字保留、哪些可以摘要，不是所有輸出一視同仁地壓縮。

原則二
可追溯回報

子系統回傳結論要附得上依據，不接受純敘述式的總結，主線才能核實。

原則三
制度化觸發

把「要不要檢查」的判斷題，換成寫進系統一律載入位置的直接指令，不依賴每次主動判斷。

應用場景：Zotero 文獻庫查詢、Google Drive 文件處理、Stata 分析紀錄、訪談逐字稿流程、RAG 知識庫檢索，任何工具輸出量大、任務會跑很多輪的 Agent 工作，都適用同一套判斷邏輯。
